# ADR-0001: apex-dispatch plugin contract

- **Status:** Proposed
- **Date:** 2026-10-06
- **Author:** solutions@getapexinsights.com
- **Plugin:** apex-dispatch v0.1.0
- **Spec:** `docs/superpowers/specs/2026-10-05-apex-dispatch-design.md` (§3, §5)

## Context

Delegation in this repo is chosen by prose: the orchestrator picks a model, a provider and a review shape by judgement, and nothing records or enforces the choice. apex-scope-loop 0.3.0 made the execution half portable and binds reviews, tiers and the green gate to an exact head, but it does not decide *who* does the work or enforce that the routed choice is what ran.

## Decision

Ship **apex-dispatch** as a separate plugin that routes and governs delegation, with apex-scope-loop as its only execution engine.

- **Surface** (built across the plan's phases; this ADR fixes the contract, not the schedule):
  - `resources/dispatch.default.json` (+ `sections.json`, `schema.json`) and a per-repo overlay `.claude/apex-dispatch/policy.json`;
  - `scripts/compile.sh [--check]` → committed artifacts (`resources/compiled/policy.json`, `hooks/hooks.json`, generated `agents/*.md`, `resources/settings-snippet.json`); a stale artifact fails `--check`;
  - `scripts/route.sh` (plan task or `adhoc --tags`): kill switches, input gate, hard floors, class table, optional decision-layer fill, tiers, fan-out, escalation, review shape; prints a `ROUTE` block and writes `<state>/dispatch/active-route.json`;
  - hooks: `pre-agent`, `pre-bash`, `pre-edit`, `pre-mcp`, `post-agent`, `subagent-start`, `subagent-stop`, `stop-gate`, `post-bash-prune`;
  - provider shims `bin/worker-*.sh` + `scripts/apply.sh`; `scripts/ledger.sh` (hash-chained JSONL, `verify`, `export-trace`), `scripts/report.sh`, `scripts/doctor.sh`;
  - skills `dispatch-route`, `dispatch-worker`; commands `route`, `run`, `done`, `report`, `doctor`, `compile`.
- **Dependency:** apex-scope-loop ≥ 0.3.0 is found as a sibling (`APEX_SCOPE_LOOP_ROOT` overrides). apex-scope-loop finds apex-dispatch by its executable `scripts/route.sh`; until that exists, apex-scope-loop behaves as if apex-dispatch were absent.
- **Namespace:** `apex-dispatch:routes/<plan-hash>/<line>`, `apex-dispatch:ledger/<plan-hash>`, `apex-dispatch:providers`; on disk only `<state>/dispatch/` and `<state>/adhoc/`, by reference to apex-scope-loop ADR-0003, which owns `.dev-plan-state/` and `ACTIVE`.
- **Governance layers, strongest first** (spec §5.3):
  - **A. Permission deny rules** in `resources/settings-snippet.json` (bypass flags, `git push --force`), applied by the user; no `ask` rules anywhere.
  - **B. apex-guardrails always-on floor:** the same bypass-flag and destructive-git denials, independent of any active route.
  - **C. Loader-enforced tool presence** in generated `agents/*.md` (`tools`/`disallowedTools`, `effort`, `maxTurns`): reviewers have no Bash and no edits; builders have no `Agent`; never `Bash(pattern)`, never `isolation: worktree`.
  - **D. Session-scoped stage lock:** an atomic `ACTIVE` lock with stage transitions written by code; GATE/REVIEW deny git mutation and writes.
  - **E. Route-enforcement hooks** (PreToolUse `Agent|Task`, `Bash`, `Edit…`, optional `mcp__`): roster, model deny-on-mismatch, budgets, stage and worktree confinement.
  - **F. Agent identity:** SubagentStart registers `agent_id → role`; per-role enforcement where the payload carries it, else the SubagentStop transcript audit.
  - **G. Provenance and script gates:** `checkpoint.sh` accepts only hook-written or shim-written verdicts at the exact HEAD; `land.sh` verifies the chain.
  - **H. Budgets, layered:** hard `maxTurns`, spawns, lanes, wall-clock and `--max-budget-usd`; advisory estimated USD.
  - **I. OS confinement, proven:** the snippet's sandbox (`failIfUnavailable`, no unsandboxed commands, provider hosts only) plus each shim's in-process probe.
  - **J. Stop hook:** blocks once per route when routed work was done inline; otherwise advisory.

  Hard rules outrank model verdicts; no new model-judged gates.
- **Decision-layer rubric ids, pinned and never renamed:** `dispatch/task-class@1`, `dispatch/size@1`, `dispatch/lens-set@1`, `dispatch/contamination@1`, `risk-tier@1`, `escalation@1` (also asserted as constants by `resources/schema.json`).
- **Overlay bounds (an allowlist, not an exception list):** the per-repo overlay configures policy within the hard rules and never weakens confinement or changes what a hard rule refers to; `compile.py` refuses anything outside this list with a named error (exit 1). Providers: only default ids (no new providers), and only `enabled`, a narrowing subset of `allowed_classes`/`roles_allowed`, a lower `max_tier`, a higher `min_acceptance`, and additions to `forbidden_flags` (union); every other field, `forced_flags` included, is fixed. Tiers: not overlayable (no change, addition, clearing or disabling); the default's tier ranks are monotonic with model strength (haiku < sonnet < opus = fable) and effort. Roles: a default role may only lose tools, gain disallowed tools, or stay read-only; `reviewer`/`adversarial-reviewer` cannot be disabled while a hard rule's review shape needs them. Hard rules: append only; an appended `route_floor` rule may not set `tier_ceiling` or be weaker than an overlapping default rule. Escalation: `max_review_rounds` and the halt rung ≤ 3, lowered only.
- **Hard-rule combination:** matching hard rules combine by max (strictest wins); `route.sh` applies every matching `route_floor` rule and keeps the strictest value of each field, and an overlay-appended rule may not be weaker than a default rule whose `when` it overlaps.
- **Policy readers:** hot-path hooks (Phase 3) and `route.sh` must read the overlay-merged policy (`compile.sh --print-merged`, or the same merge and checks), not only `resources/compiled/policy.json`, which is the default policy alone.
- **Generated agents omit `model:`** deliberately: frontmatter `model` is a default the per-call parameter overrides, not a pin (spec §5.3 C), so the model is enforced by `pre-agent.sh` deny-on-mismatch; the repo CLAUDE.md `model:` convention applies to hand-written agents. `agents/` is fully generated: `compile.sh --check` flags any `agents/*.md` that is not an expected artifact, and compares bytes exactly (a CRLF copy is stale).
- **Hook registration:** `scripts/compile.sh` registers in `hooks/hooks.json` only the hook scripts that exist under `hooks/`, each through a fixed event/matcher table; per-repo policy never changes registration (disabled features no-op in bash). With no hook scripts present the file is `{"hooks": {}}`.
- **Hook contract (Phase 3.1: `pre-agent`, `pre-bash`, `pre-edit`, `pre-mcp`; Phase 3.2: `post-agent`, `subagent-start`, `subagent-stop`, `stop-gate`, `post-bash-prune`):**
  - **Registration.** PreToolUse, matchers `Agent|Task`, `Bash`, `Edit|Write|MultiEdit|NotebookEdit`, `^mcp__`; PostToolUse `Agent|Task` (`post-agent`) and `Bash` (`post-bash-prune`); PostToolUseFailure `Agent|Task` (`post-agent`); SubagentStart and SubagentStop `^(apex-dispatch|apex-scope-loop):`; Stop without a matcher (spec §5.1). Command `bash "${CLAUDE_PLUGIN_ROOT}/hooks/<hook>.sh"`, `timeout: 10`, generated by `compile.sh`. Phase 0 did not exercise matcher syntax, so each hook also checks `tool_name` (or the `agent_type` prefix) exactly and no-ops on anything else (a regex `Agent|Task` also matches tools such as `TaskStop`). The spec's `if: Bash(<runner> *)` filter on `post-bash-prune` is not used; the hook matches runners itself.
  - **Engagement.** Each hook is a no-op (`{}`) unless the run's `ACTIVE` lock exists. The state root comes from apex-scope-loop's own `_lib.sh` (`apex_state_base`: `APEX_STATE_ROOT`, else `git rev-parse --path-format=absolute --git-common-dir`), resolved from the payload's `cwd`, so the base checkout, the plan worktree and shim worktrees see one lock. An owner whose stage is `DONE` or whose plan has landed is no run; `APEX_DISPATCH_MODE=off` is a no-op. The lock governs the repository, not one session: any session working in it is governed while the lock is held (Phase 0 spike 12: a nested `claude -p` reports its parent's `session_id`).
  - **Output.** Exactly one JSON object on stdout and exit 0, always (an `EXIT` trap prints `{}` if nothing else was printed), with two documented exceptions that exit 2 with the reason on stderr and still print `{}`: `subagent-stop`'s audit refusal and `stop-gate`'s block (Phase 0 spike 10: exit 2 blocks once, and the re-fired event carries `stop_hook_active`, which both hooks always pass). `post-agent` may answer with PostToolUse `additionalContext` (spike 9: delivered). A denial is `hookSpecificOutput {hookEventName: PreToolUse, permissionDecision: deny, permissionDecisionReason}`. The only allow is `pre-agent`'s model fill: `permissionDecision: allow` with a full-object `updatedInput`. Unparseable stdin or an internal error fails open: `{}`, a stderr advisory and a `hook_error` ledger row when the run's ledger is writable. Each denial is also a `hook_advisory` row (`denied: …`); each allowed spawn is a hook-sourced `spawn_request` row (role, effective model, `subagent_type`, `tool_use_id`, stage).
  - **Hot path.** Without a lock the hooks run bash only (one `git rev-parse`); `python3` (`scripts/lib/hooks.py`) starts only under a lock, to parse JSON and tokenise the command. A governed call measures about 0.1–0.2 s; smoke asserts under 2 s for `pre-bash` and for a `subagent-stop` transcript audit (bounded to the transcript's last 4 MB and 2000 tool uses). `stop-gate` adds one `git status` (5 s timeout; a timeout counts as clean).
  - **Which route applies.** `<D>/active-route.json` when it is READY and belongs to the lock owner (same `plan_hash` and `line`, or the same ad-hoc id). Route modes `table`, `decision` and `escalated` are enforced. In `baseline`/`shadow` the roster, model, budget and gate binding are recorded, not enforced (0.2.0 behaviour); the safety rules below still apply. A lock with no matching READY route denies every spawn ("nothing is dispatched").
  - **pre-agent enforces:** depth 1 (a spawn whose payload carries `agent_id`, or an `apex-dispatch:`/`apex-scope-loop:` `agent_type`, is denied, per Phase 0 spike 5); HALT (`APEX_HALT=1`, the HALT files apex-scope-loop honours, a halted checkpoint); the roster (`subagent_type` must be `apex-dispatch:<role>` with the role on `ROUTE_ROSTER`); the model on builder-side roles by deny-on-mismatch against `ROUTE_MODEL`, then, when `model` is absent, `updatedInput` setting it (enum `sonnet|opus|haiku|fable`; `updatedInput` is last-writer-wins, spike 4, which is why deny comes first); `ROUTE_BUDGET_SPAWNS` over builder-side `spawn_request` rows (reviewers are bounded by the review shape and the three-round cap instead); `ROUTE_BUDGET_MINUTES` since the route row; `ROUTE_BUDGET_USD` (Phase 3.2) for builder-side spawns, against the sum of the route's hook/shim `worker_run` rows (a row's `usd`, else its usage × the overlay-merged tier price of its resolved family); no builder-side spawn during GATE/REVIEW; a reviewer (`reviewer`, `adversarial-reviewer`, `reviewer-exec`) only when `<state>/gate/last.json` is `PASS` or `SKIPPED` at the worktree's HEAD and (Phase 3.2) no builder-side agent of the route is live in the registry, and allowing one sets stage `REVIEW`. An ad-hoc route has no plan line and so no gate result: its reviewers need a committed, clean HEAD instead (the Acceptance command is the orchestrator's to run first; `/apex-dispatch:run`) (under the `.active.lock` flock `_lib.sh` uses). Leaving GATE or REVIEW is a re-route (`iterate.sh` or `route.sh plan` re-acquire the lock at BUILD).
  - **pre-bash enforces** (on the tokenised command; nested `bash -c`/`sh -c`/`eval`/`$(…)`/`find -exec`/`git submodule foreach` strings and backtick bodies, quoted or not, are parsed too; heredoc bodies are skipped; leading reserved words (`if then else elif fi do done while until esac ! { } time`) are peeled off like `env` and other wrappers, and a `for`/`select`/`case` header is a word list, not a command, so the body after `do`/`then`/`)` is checked as its own command): tamper hardening (inline, `env`, `export`/`declare` assignments or `unset`/`env -u` of `APEX_GIBSON=0`, `APEX_HALT` to anything but `1`, and any change to `APEX_DISPATCH_MODE`, `APEX_DISPATCH_ENFORCE`, `APEX_DISPATCH_POLICY`, `APEX_FORCE_UNLOCK`, `APEX_STATE_ROOT`, `APEX_SCOPE_LOOP_ROOT`, `APEX_DISPATCH_ROOT`, `APEX_REVIEW_CAP`, `APEX_ERROR_BUDGET`, `APEX_ESCALATE_AFTER`); writes (`rm`, `mv`, `cp`/`install`/`ln`/`rsync` destinations, `touch`, `mkdir`, `tee`, `truncate`, `chmod`/`chown`, `sed -i`, `perl -i`, `dd of=`, `patch`, `find -delete`, and every output redirect) into the protected paths below, `touch …/HALT` excepted; direct `python` invocations of apex-dispatch's ledger (a path that resolves to this plugin's `scripts/lib/ledger.py` or any `apex-dispatch/scripts/lib/ledger.py`, `-m ledger` (the interpreter's own first `-m` naming exactly `ledger`; `pytest -k ledger` and `-m pytest tests -m ledger` pass), or `-c` code with a statement, at the start or after `;`/a newline, `import …ledger…` (`import ledger as L`, `import os, ledger`; not `import app.ledger`) or `from ledger import`, a `ledger.append(` call, or that path; `pytest tests/test_ledger.py` is not the ledger); provider CLIs (`claude -p`, `codex`, `grok`, `opencode`, `aider` and the policy's binaries, also through `npx`/`bunx`/`pnpm dlx`/`uvx`/`pipx`) except `--version`/`--help`, so they run only through `bin/worker-*.sh`, and shims only from the orchestrator or `provider-runner`; the layer-A bypass families (`--dangerously-*`, `--yolo*`, `--always-approve*`, `--full-auto*`, `danger-full-access`) in the arguments of any command except text tools (`echo`, `printf`, `grep`, `rg`, `git`, `sed`, `awk`, `cat`, …), where they are data, so this repository can be grepped and committed about; layer A's deny rules still match the raw string; a provider's own `forbidden_flags` on that provider's command or shim; during GATE/REVIEW, every git mutation (anything outside a read-only allowlist: status, diff, log, show, rev-parse, ls-files, fetch, `branch --show-current`, `stash list`, …; unknown subcommands and aliases count as mutations) and every write whose target is inside the plan worktree or the base checkout (or cannot be resolved because it contains `$`); for read-only roles identified by `agent_type`, the same git and write rule at any stage.
  - **Git configuration and repository internals** (apex-scope-loop ADR-0003 §4 leaves these to this hook), denied at any stage of a run: `git config` writes in any scope (`--global`, `--system`, `--local`, `--worktree`, `--file`; `set`/`unset`/`--add`/`--replace-all`/`--unset*`/`--rename-section`/`--remove-section`/`--edit`, or two positional arguments), while reads (`--get*`, `--list`, `get`, `list`, one positional name) pass; `git update-index --assume-unchanged|--skip-worktree|--fsmonitor-valid` (the `--no-…` forms pass; `--chmod`, `--cacheinfo` and `--index-info` change staged content that `git status` shows, so they are left to the stage lock); `git sparse-checkout` other than `list`; `git -c`/`--config-env` with a `core.*` (except the cosmetic `core.editor` and `core.pager`), `filter.*`, `diff.*`, `merge.*`, `include.*` or `includeIf.*` key on a mutating command (`core.hooksPath`, filter and merge drivers included); `GIT_CONFIG*` environment on a mutating git command, and any `export GIT_CONFIG*`; writes into any `.git/` path (`info/exclude`, `info/attributes`, `info/sparse-checkout`, `hooks/`, `config`, a worktree's gitdir), `~/.gitconfig`, `~/.config/git/` and `/etc/gitconfig`.
  - **pre-edit enforces:** protected paths for every role, at every stage: `.dev-plan-state/` (and the resolved state root), `.claude/apex-dispatch/`, `.claude/settings*.json`, `.claude/hooks/`, `.mcp.json`, any `.git/` path, git configuration files, and the installed apex-dispatch and apex-scope-loop plugin directories (their `hooks/hooks.json` included; a `hooks/hooks.json` elsewhere, such as plugin source in a repository under development, is ordinary work). apex-scope-loop puts the plan worktree at `<state>/worktree`, inside `.dev-plan-state/`: paths inside the checkpoint's `worktree_path` are work, not run state, except a `.dev-plan-state/` nested in it; the worktree root may be a write destination (`cp x .`, `mv a/b .`, `rsync -a v/ .`, `patch`, `chmod -R .`, `touch .`) but never removed or moved: `rm`/`rmdir` of it, `mv` with it as a source (the `-t`/`-vt`/`-tDIR`/`--target=`/`--target-directory` forms are recognised for cp/mv/install/ln), and `git worktree remove|move` of the plan worktree (the target resolved against the cumulative `git -C` directories; a `$` in either is denied) are denied. A deleting `find` (`-delete`, or `-exec`/`-ok` running rm/rmdir/unlink/shred/mv) whose start point *resolves* to a worktree root (`.`, `../worktree`, an absolute path or `cd src && find ..` alike) must carry a `-name`/`-iname`/`-path`/`-regex`/`-empty` filter and no `!`, `-not`, `-o`/`-or` or `-prune` (run such finds from a subdirectory or with positive filters only); a start point containing `$` or a backtick cannot be resolved, so it is judged as a possible root by the same rules (`find "$OUT" -name '*.o' -delete` passes, `find "$OUT" -delete` does not); and no `-name`/`-iname` value may match `.git` or the root's own name, nor a `-path`/`-regex` value `<start>/.git` or the start itself: otherwise it could delete the root or the worktree's `.git` link file. `rsync` with `--del`, any `--delete*` or `--remove-source-files` into a worktree root, or into a destination containing `$`, needs an exact `--exclude=.git`/`--exclude=/.git` (or `-f '- .git'`) and no `--delete-excluded`; other ways to delete that file (a script, an unfiltered `git clean -x`, which only the GATE/REVIEW stage lock refuses) are beyond string matching, and apex-scope-loop's dirty check reports the broken worktree. Everything around the root (`checkpoint.json`, `gate/`, `dispatch*/`, HALT, `ACTIVE`) stays protected. The same rule applies to pre-bash write targets, which are resolved with symlinks followed; then no writes during GATE/REVIEW; none from read-only roles (`agent_type`); none outside the plan worktree (the checkpoint's `worktree_path`, else the plan's checkout), except scratch files under `/tmp`, `/var/tmp` or `$TMPDIR` that lie outside every checkout; with `FANOUT=lanes`, none outside the union of the lanes' `Paths:` globs (read from the plan with apex-scope-loop's `planlib`). Paths are resolved against the payload `cwd` with symlinks followed.
  - **pre-mcp enforces:** nothing unless the overlay-merged policy sets `mcp.default_deny: true`; then an `mcp__<server>__<tool>` call passes only when `mcp.servers_allow`, or the calling role's `mcp_allow` (by `agent_type`), names the server, the tool, or a `mcp__…*` prefix.
  - **Agent registry (Phase 3.2).** `subagent-start` writes `<D>/agents/<agent_id>.json` (`agent_id` must match `[A-Za-z0-9_-]{1,64}`; role from the `agent_type` prefix; the route id; `started_at`) and a hook-sourced `spawn` row; `subagent-stop` (and `post-agent`, for a completed foreground agent) records `stopped_at`. `post-agent` also records the stop of any foreground agent whose response carries an `agentId` (completed, failed or interrupted). The **live set** is the current route's registrations without a stop that are younger than the route's `ROUTE_BUDGET_MINUTES` (120 when unset), so a lost SubagentStop delays review by at most that, never wedges it; a re-route (a new route id) also clears it, and the denial says so. SubagentStart injects nothing: Phase 0 confirmed its payload (spike 7) but not `additionalContext` on that event, so the role contract stays in the generated agent and the brief.
  - **post-agent (Phase 3.2)** keys on Phase 0 spike 6's `tool_response` (`agentId`, `resolvedModel`, `status`, `totalDurationMs`, `totalToolUseCount`, `totalTokens`, `usage`; `modelsUsed` only if present): one `worker_run` row per `tool_use_id` (provider `claude-session`, role, `exit_code` 0, or 1 on PostToolUseFailure, `resolved_model`, usage normalised to `input/output/cache_read/cache_write`, `duration_ms`, `tool_count`, `usd_estimate`). Usage is the agent's aggregate, so deduplication is per tool use, not per `message.id`. A response with neither `resolvedModel` nor usage (a background launch returns before the agent ran) is a `hook_advisory`, not priced: background agents' usage stays unverified until Claude Code reports it. A builder-side run whose resolved family differs from `ROUTE_MODEL` writes `model_mismatch` and tells the orchestrator through `additionalContext`; this is advisory (the spawn already ran; `pre-agent`'s deny-on-mismatch is the enforcement), as the spec places verification, not denial, here.
  - **subagent-stop (Phase 3.2).** For `reviewer`, `adversarial-reviewer`, `reviewer-exec` and `apex-scope-loop:gibson-reviewer`: the verdict comes from `last_assistant_message` (spike 7) and **fails closed**: every line `verdict: <value>` (any case, markdown emphasis ignored) is read, a value exactly `APPROVE` is APPROVE, one starting `REQUEST CHANGES`/`REQUEST_CHANGES`/`request-changes` is REQUEST_CHANGES, anything else UNPARSED; the record is APPROVE only when every verdict line is APPROVE, else the last non-approving value, and UNPARSED when there is no verdict line at all — an unreadable verdict is recorded and blocks `complete` at that head like a REQUEST_CHANGES; the lens the last `LENS: <lens>` line (emphasis such as `**LENS:** Security` ignored), normalised to one of the six canonical lenses `correctness`, `security`, `consent-pii` (`Consent / PII`, `PII`), `money`, `performance`, `maintainability` (or `adversarial`); an unknown lens is no lens (role `reviewer`, which does not count toward the six). The raw record `<D>/reviews-raw/<agent_id>.json` is written once (exclusive create; a re-fired stop never rewrites it) with `record_id` = `<agent_id>-<16 hex>`, `line` (the route's, else the lock owner's), `head_sha` (and `sha`) = the plan worktree's HEAD that `subagent-start` stamped (`head_at_start`) when the reviewer started (else `git rev-parse HEAD` at stop); if HEAD moved while it ran the record keeps the start HEAD and carries `stale`, which `checkpoint.sh review` refuses, so a slow review of X is neither credited to nor blocks Y; `role` (`adversarial` for `adversarial-reviewer` or a gibson `LENS: adversarial`; `lens:<lens>` for a lens; else `reviewer`), `lens`, `verdict`, `agent_id`, `route`, `provider: claude-session`, `family: anthropic`, `plan_hash`; plus a hook-sourced `verdict` row with the same `record_id`. The file is named by `agent_id`, not `record_id` (the spec's `reviews-raw/<agent_id>.json`; `checkpoint.sh review --agent-id` reads it). No verdict line: an `UNPARSED` record and `verdict` row (fail closed). `post-agent` treats only explicit terminal statuses (`completed`, `failed`, `error`, `cancelled`, `interrupted`, `killed`, `aborted`) as a stop; a missing or unknown status leaves the agent live. **Transcript audit**, for every read-only role (the reviewers, `researcher`, `diagnoser`, `provider-runner`): the subagent transcript (`agent_transcript_path`, last 4 MB) is scanned for tool uses whose result is not an error (a hook-denied attempt is not a violation): Write/Edit/MultiEdit/NotebookEdit, Agent/Task, and Bash commands that `pre-bash`'s rules refuse that agent, judged with its own `agent_type` exactly as live `pre-bash` judged it (a read-only role: git mutation, writes into the checkout, run state, provider CLIs; `provider-runner` may run `bin/worker-*.sh`; `gibson-reviewer`, which has no apex-dispatch role, is refused only what `pre-bash` refused it). The stage used is the one at stop time, which is the stage the review ran in (REVIEW). A hit writes `policy_violation` (once per agent), replaces the review record with `{refused: …, head_sha, line, route}` (which `checkpoint.sh review` refuses by name) and exits 2 once; with `stop_hook_active` it exits 0. Per Claude Code's SubagentStop semantics exit 2 returns the reason to the subagent (not the orchestrator, as the spec text says), so the orchestrator learns of it from the refused record and the ledger.
  - **stop-gate (Phase 3.2).** Exit 2 (spike 10) at most once per route (a `hook_advisory` row with `blocked: true` marks it) and at most eight times per run, only while the owner's READY route is enforced (`table`/`decision`/`escalated`) and the stage is BUILD, when: HEAD moved since the route row and no hook/shim spawn or worker row exists for it (routed work done inline, the spec's rule); or the plan worktree is dirty (run state excluded) while none of the route's builder-side agents is live. Live background builders never spend a block: ending the turn while they run is the documented `run_in_background` flow. Escapes: `stop_hook_active`, HALT (any kill switch), no lock, a DONE/landed owner, stage GATE/REVIEW, a baseline/shadow or missing route. An open route with no spawn yet is a one-time `hook_advisory`. The spec's narrower rule (inline work only) is widened to one "work would be lost" case (a dirty worktree with no builder running); each is still once per route.
  - **post-bash-prune (Phase 3.2)** is record-only: Phase 0 spike 9 showed a command hook's `updatedToolOutput` is not applied to Bash, so it keeps the full output of a recognised runner (`pruning.runners`, substring match on the command) longer than `pruning.max_lines` at `<D>/logs/<tool_use_id>.log` and writes a `hook_advisory` (runner, line count, failure-line count, log path). It does not trim or summarise what the model sees; the spec's observation masking (§8 step 5) is not available on 2.1.289.
  - **Stage transitions (spec §5.3 D), complete:** `iterate.sh`/`route.sh` → BUILD; `green-gate.sh check` PASS or SKIPPED → GATE, written by apex-scope-loop under the same `.active.lock` flock and only from BUILD (a re-run during REVIEW or after DONE leaves the stage alone); `pre-agent` allowing a reviewer → REVIEW (refused while the live set holds a builder-side agent); `checkpoint.sh complete` → DONE. The spec's GATE allowlist (only the compiled gate command runs) is not implemented as an allowlist: GATE is enforced like REVIEW (no git mutation, no writes in the checkout), and `green-gate.sh` itself runs as one script call.
  - **Still deferred:** confining each lane's builder to its own lane's globs (pre-edit confines to the union, because the Agent payload does not say which lane a later Edit belongs to); per-agent tool-call budgets; read-only command allowlists for `reviewer-exec` (opt-in, disabled by default; its transcript is audited); builder-specific git restrictions and Bash worktree confinement by role; reviewer family diversity at spawn time (every in-session spawn is Claude-family and the Agent payload carries no provider, so diversity is a `checkpoint.sh complete` check and a Phase 4 shim concern); output trimming (above); injecting the role brief at SubagentStart (above).
  - **Deviations from the spec text, and why:** a provider's own `forbidden_flags` apply to that provider's command and shim, not anywhere (`--bare`, `-a` and `--auto-commits` would deny `git clone --bare`, `ls -a`); the bypass families do apply anywhere. Agent identity (spec §5.3 F) is used directly from the payload rather than gated on `doctor.json`, because Phase 0 spike 5 confirmed it on 2.1.289; doctor's live probe stays `unverified`.
  - **What string matching can and cannot catch.** The trust model is non-malicious agents: the hooks stop accidents and realistic misuse, they are not a sandbox. They see one command string. They cannot see what a script, a Makefile target, `python -c`, `node -e`, an alias, a variable (`$CMD`), an encoded payload or a file written now and executed later does; nor the targets of tools that write without saying so (`npm install`, a test run, an editor). Commands with unresolvable targets are denied only where a stage or role forbids writes. Layers A (deny rules), C (tool presence), G (provenance at HEAD in `checkpoint.sh`/`land.sh`), I (OS sandbox) and apex-scope-loop's positive worktree inventory remain the backstops; a determined adversary needs the OS sandbox, not these hooks.
- **Ledger (Phase 2.4):** one writer (`scripts/lib/ledger.py`, imported by `route.py`, called by `ledger.sh append`); events and required fields in `resources/ledger-events.json`; rows stamped `seq, event, ts, source (hook|shim|cli), route_id, head_sha, route_mode, doctor_profile, prev_hash, hash` (sha256 over the canonical row without `hash`), appended under `flock` with a `ledger.head` anchor so truncation is detectable. `verify` names the first tampered, deleted, reordered or truncated row. An append is refused when `ledger.head` disagrees with the last row, except for the one-row-behind crash case, which it repairs. Provenance events (`route`, `spawn_request`, `spawn`, `worker_run`, `verdict`) are written in-process only, and the `ledger.sh append` CLI refuses them. `evidence --line N --head SHA [--plan-hash H]` (what `checkpoint.sh complete` requires) holds when the chain verifies, a READY route row `r-<H>-L<N>-k` exists for this plan with its `line`/`plan_hash` fields agreeing and its `head_sha` on HEAD's history, and a hook- or shim-sourced `spawn_request`/`spawn`/`worker_run` row with that route's id is on HEAD's history. The source stamp is caller-asserted. Phase 3.2 adds the events `model_mismatch` and `policy_violation` (not provenance; the hooks write them). While a run holds the `ACTIVE` lock, `pre-bash.sh` (Phase 3.1) denies direct `python … ledger.py` / `-m ledger` / `-c '…ledger…'` invocations, but that is string matching (see the hook contract), so evidence is still not proof against a determined orchestrator: it raises the bar from free to deliberate tampering. `export-trace` emits apex-agent-observability's AgentTrace line shape. `doctor.sh` writes `doctor.json` with `ok|warn|fail|unverified|skipped` per check; checks that need a live session are `unverified`, never `ok`.
- **Enforcement switch (on by default since Phase 3.2):** apex-dispatch creates `<state>/dispatch/` (which puts `checkpoint.sh` into provenance mode) when `hooks/subagent-stop.sh` exists in the plugin (it ships since Phase 3.2, so this is the default for every install), when `APEX_DISPATCH_ENFORCE=1`, or when `<state>/dispatch/` already exists. `APEX_DISPATCH_ENFORCE=0`, set by the human before a run, keeps the transitional `<state>/dispatch-shadow/` (the hooks still enforce the route and record everything there, but apex-scope-loop ignores it for provenance); `pre-bash` refuses any change to the variable during a run, and a state whose `dispatch/` exists stays enforced. The first creation of `<state>/dispatch/` records `dispatch_enforced: true` in `checkpoint.json` (`mark_enforced` reads the checkpoint first and takes no lock when it is already set), and `checkpoint.sh review|complete` and `land.sh` then refuse if the directory disappears. **Reviewer family diversity** uses one rule in `doctor.sh` (`tier_c_diversity`, `second_families`) and `checkpoint.sh complete`: `ledger.second_families`, a provider other than `claude-session` that `doctor.json` shows enabled and available (`claude-p` also needs `claude_p_auth: available`) **and** whose `bin/worker-<provider>.sh` exists and is executable, since `pre-bash` refuses provider CLIs outside the shims. Until the Phase 4 shims ship the list is empty, so Tier C diversity degrades to a ledgered warning and never wedges `complete`. **A non-approving review is final at its head:** in provenance mode `complete` refuses while any hook/shim `verdict` row or raw record for the line at HEAD is not APPROVE (a record the audit refused included); only a new commit supersedes it, and typed (`declared`) records never count toward the lens/adversarial requirements. End to end under enforcement: the route row (route.sh), `spawn_request` (pre-agent), `spawn` (subagent-start) and `worker_run` (post-agent) rows satisfy `ledger.sh evidence`; each reviewer's raw record satisfies `checkpoint.sh review --agent-id`; `complete` then passes (smoke check 58).
- **Tier C floor tags:** the `tier-c-floor` hard rule's `tags_any` is `security, migration, tier:c, auth, pii, money, billing`; those tags route as class security (G12, single fan-out, never a lane). The Tier C *risk* tag set (`security, tier:c, tier-c`) stays identical to `checkpoint.sh`'s `forced_c`; the floor tags only tighten the route.
- **Compatibility:** Claude Code 2.1.251+, git 2.40+, bash 4+, python3 3.8+ stdlib; no ruflo.

## Consequences

- Delegation becomes a recorded, enforced decision rather than prose.
- Two plugins must stay version-compatible; `doctor.sh` checks the sibling's version.
- The smoke contract grows per phase: compile `--check`, route dry-runs, hooks on garbage stdin emit exactly one JSON object and exit 0 (with and without a lock), crafted deny cases for each hook deny and their read-only twins pass, a governed hook call stays well under its timeout, ledger verify passes a sample chain and fails a tampered row, no forbidden flags in `bin/`, generated reviewers have no Bash.
