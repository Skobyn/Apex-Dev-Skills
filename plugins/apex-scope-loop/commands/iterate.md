You are iterating one phase of the apex-execute for `$ARGUMENTS`.

Invoke the `apex-execute` skill and execute one iteration:

In the steps below, `$S` stands for `${CLAUDE_PLUGIN_ROOT}/skills/apex-execute/scripts`, where the helper scripts ship with this plugin. Use that absolute path in every command; no repo-local `.claude/skills` copy is needed.

1. Run `$S/iterate.sh $ARGUMENTS` to get the brief. It returns the next unchecked, unblocked task along with `WORKTREE:`, `BRANCH:`, `LINE_NO:`, `HEAD_SHA:` (the worktree head now), `TASK_BASE:` (this task's diff base, fixed when the task is first briefed), `HARNESS:`, `LESSONS:`, `CONSECUTIVE_FAILURES:`, and the review-loop fields (ADR-0004): `THREAT_MODEL:` (its source, then the text as `  > ` lines), `LAST_REVIEWED:`, `REVIEW_ROUND:`, `REVIEW_MODE:`, `ADVERSARY_BUDGET:` and `BACKLOG:`, plus `SINCE:` (= `TASK_BASE`, the value for every `--since` and for round 1's SINCE; `HEAD_SHA:` is only the head at brief time, never a diff base), `REVIEW_CAP:`, `REVIEW_DIRECTIVE:`, `FROZEN:`, `THREATS:`, `FINDINGS:` (this task's findings file and its open count), `KNOWN_DEFECT_CLASSES:` and, when a finding class recurred across tasks, `LESSON_SUGGESTED:` — run that exact `lessons.sh … add` command after filling in the root cause and the harness fix. If `STATUS: HALTED` comes back, report the `HALT_REASON:` and stop. Never work around a kill switch.
2. **Recall before you act.** If `LESSONS:` is non-zero, run `$S/lessons.sh $ARGUMENTS recall <tags>` and put the relevant lessons into every builder's prompt.
   If the task is a `[docs]` or hygiene task and `BACKLOG:` is non-zero, run `$S/backlog.sh $ARGUMENTS list`, hand the open items to the builders as part of the task, and mark each one with `$S/backlog.sh $ARGUMENTS done <ID> --line <LINE_NO> --sha <the fixing commit>` once its fix is committed: it stays pending until this task's `complete` confirms it, and `fail` or `rewind` reopens it.
3. Parse the task's tags (`[backend]`, `[security]`, etc.) and its `Swarm:` directive.
4. **Execution is worktree-bound.** The whole plan runs inside the worktree on the brief's `WORKTREE:` line (branch `BRANCH:`). Every agent must `cd` into that worktree and make ALL code edits there, never in the base checkout. Pass the worktree path explicitly in each Agent prompt. If `WORKTREE:` is empty, init.sh was run with `APEX_NO_WORKTREE=1`, and only then do you operate in the base checkout.
5. **Build.** Give every builder the brief's `THREATS:` list, `KNOWN_DEFECT_CLASSES:`, and the handback template `${CLAUDE_PLUGIN_ROOT}/skills/apex-execute/resources/templates/builder-handback.md` (threat → failing-first test with real files, the real gate or the real seal → the mutant that turns it red; the tests that use real files; one line per threat). Working agreement for builders: **if a hook or filter rejects text, stop and report the exact message; never obfuscate around it.** Dispatch the builder swarm with the Agent tool: all spawns in **one message**, `run_in_background: true` where it applies, each scoped to the worktree path. Wait for the verdicts and don't poll, because the harness notifies you on completion. Then commit the task's work on the worktree branch.

When `HARNESS: gibson` (the default), steps 6–9 apply. With `HARNESS: off`, skip them and go straight to step 10.

6. **Green gate.** Run `$S/green-gate.sh $ARGUMENTS check`. It needs a clean, committed worktree and fails on any step that is red now but was green at the fork point. A `PREEXISTING` red step isn't this task's failure, but report it anyway. On `GATE: FAIL`, go to step 11.
7. **Tier.** Run `$S/risk-tier.sh $ARGUMENTS <LINE_NO> --since <TASK_BASE>` (the task's own tags are read from the plan). Re-run it after every fix commit: `complete` refuses a tier recorded for an older head.
8. **Independent review (never grade your own homework).** Dispatch the `gibson-reviewer` agent in a fresh context, separate from every builder, and pass it WORKTREE, the new head SHA (`git -C <WORKTREE> rev-parse HEAD`), SINCE (= `REVIEW_SINCE`), TASK, ACCEPTANCE, TIER, `TIER_REASONS` (every line, verbatim: an overridden or unanticipated Tier C signal must reach every reviewer), `THREAT_MODEL` (the brief's text, **verbatim**, to every reviewer including lens and adversarial ones), `MODE`, and `BUDGET` (= `ADVERSARY_BUDGET`).
   - **Mode first.** After step 7 (the tier is now recorded for this head), run `$S/checkpoint.sh $ARGUMENTS review-mode <LINE_NO>` — the brief's `REVIEW_MODE` was computed before the build and predates any tier rise. Use its `REVIEW_MODE` and `REVIEW_SINCE` for this round.
   - **Freeze and snapshot.** At review dispatch run `$S/checkpoint.sh $ARGUMENTS freeze <LINE_NO> <sha> --reviewers <n> --mode <REVIEW_MODE>` (n = the verdicts you will record this round) and `$S/snapshot.sh $ARGUMENTS <sha>`; give every reviewer the printed `REVIEW_SNAPSHOT:` path (read-only, one per commit; set `APEX_SNAPSHOT_SETUP` for a build step) and tell them not to build their own copy. While frozen, `review` of another SHA is refused: fixes wait and land as **one batch** after the round. `freeze --mode verify` is refused when the tier rose above every full round of the attempt or a Tier C attempt has no full-mode adversarial review at Tier C; record every verdict of the round with the same `--mode` (a frozen round's mode is the default). `complete` refuses unless some round of the attempt was full at the effective tier and, for Tier C, had a full-mode adversarial review at Tier C. The freeze lifts when the n verdicts are in (or `checkpoint.sh unfreeze <LINE_NO>`). With apex-dispatch hooks, freeze also moves the lock GATE → REVIEW, where commits are already refused.
   - **Findings.** Record every finding from every reviewer: `$S/findings.sh $ARGUMENTS add <LINE_NO> --severity blocking|non-blocking --class <defect-class> --at <file:line> --sha <sha> "<one-line mechanism>" --from <reviewer>`. A defect is counted once: the same class and file:line is the same entry (a new mechanism is added to its list; a blocking re-report reopens a closed one, a non-blocking one never does). Non-blocking findings are residuals: findings.sh copies them to the backlog and they never reopen a round. Close a finding once a reviewer verified the fix: `$S/findings.sh $ARGUMENTS close <LINE_NO> <ID> --reason "<evidence>"`.
   - **Round 1** (`REVIEW_ROUND: 1`) is the full review: `MODE: full`, SINCE=`<TASK_BASE>`. For Tier C it carries the one full adversarial pass of the attempt.
   - The brief's `REVIEW_MODE` decides: it is `full` (SINCE=`TASK_BASE`) in round 1, whenever the tier rose above every tier reviewed in the attempt, and while a Tier C attempt has no adversarial review yet.
   - **Round 2 and later** are otherwise verify-only: `MODE: verify`, SINCE=`<LAST_REVIEWED>`, and `PRIOR_FINDINGS` = the open items of `$S/findings.sh $ARGUMENTS list <LINE_NO> --open` (the brief's `FINDINGS:` file). Reviewers (the adversarial one included) re-verify each prior finding by experiment, then hunt only in the fix delta and its blast radius; they do not restart the attack on the whole surface. After a REQUEST_CHANGES, re-run `$S/iterate.sh $ARGUMENTS` (same task) before the fix to get `LAST_REVIEWED` and `REVIEW_ROUND` for the next round.
   - **Severity bar.** `[blocking]` means a realistic actor under the stated threat model can cause it in an ordinary flow, or Acceptance is unmet, or tests were weakened. At most `BUDGET` findings per pass are blocking. Record every `[non-blocking]` finding (and anything outside the threat model) in the hardening backlog: `$S/backlog.sh $ARGUMENTS add <LINE_NO> "<finding>" --from <reviewer>`. Never carry them in your own context, and never fix them in this task unless the human promotes one. With apex-dispatch routing the task (the brief has `ROUTE_STATUS: READY` in mode `table`, `decision` or `escalated`), its `pre-agent.sh` allows only the route's roster: run `route.sh review-shape <ROUTE_ID> --tier <TIER>` and dispatch `apex-dispatch:reviewer` (one per lens for Tier C) and `apex-dispatch:adversarial-reviewer` as it prints, instead of `gibson-reviewer`.
   - Tier A: one reviewer. Tier B: one reviewer covering all six lenses.
   - Tier C: a **fan-out**, with one `gibson-reviewer` per lens (six, in one message), then one more with `ADVERSARIAL: true` to try to refute the approvals.
   - Record each outcome with `$S/checkpoint.sh $ARGUMENTS review <LINE_NO> <sha> APPROVE|REQUEST_CHANGES`. With apex-dispatch installed (`<state>/dispatch/` exists), record it from the reviewer's hook-written record instead: name the reviewer and pass `--agent-id <the reviewer's agent id>`; the role comes from the record, so a lens reviewer ends with `LENS: <lens>` and the adversarial pass with `LENS: adversarial`. Any REQUEST_CHANGES means the builders fix, commit, and repeat from step 6. If `checkpoint.sh review` prints `ASK_HUMAN: pending`, the frozen round still has verdicts outstanding: record the rest of the round first, then ask (do not halt yet). If it prints any other `ASK_HUMAN:`, stop looping: halt with `$S/checkpoint.sh $ARGUMENTS halt "awaiting human review waiver line <LINE_NO>"` and ask with the **Ask Contract** (below) whether to accept the residual risk or keep fixing, listing the open blocking findings and ending with "Reply with a message that starts with `waive <LINE_NO>` (a remark may follow) to accept the residual risk, or `keep fixing`." A reply that does not start with `waive <LINE_NO>` is refused by `waive`; ask again rather than interpreting it. On `waive`, record their literal reply and the residual risk with `$S/checkpoint.sh $ARGUMENTS waive <LINE_NO> <sha> "<reply>" "<residual risk accepted>"`, add the waived findings to the backlog, and go to step 9/10. A waiver covers only the REQUEST_CHANGES verdicts at that exact SHA (this epoch and attempt): the gate, the tier, G12 for Tier C and Acceptance still apply, and the completion is recorded as `waived`, never as approved. Never record a waiver the user didn't give. Whenever apex-dispatch's hooks are installed (enforced or not: `APEX_DISPATCH_ENFORCE=0` and `dispatch-shadow/` included), a passing gate moved the lock to stage GATE and the hooks refuse commits and writes until the task is re-routed, so re-run `$S/iterate.sh $ARGUMENTS` (same task, stage BUILD) before the fix. The cap (`REVIEW_CAP:`, default 3, or the plan's `Review: cap=<n>`) counts only rounds that requested changes; when `review` refuses with `REVIEW_CAP`, treat it as a failure (step 11) or ask the human for a waiver. A plan's `Review: lenses=… adversarial=…` directive may narrow the lenses and drop the adversarial pass for Tier A/B; for Tier C it may narrow the lens fan-out to no fewer than 3 distinct lenses, plus the lens of each Tier C signal (`SIGNAL_LENSES`), and the adversarial pass and G12 stay; `complete` records what the directive changed.
   - **Tier changes.** A reviewer who finds the tier too low says so first; record it with `$S/risk-tier.sh $ARGUMENTS <LINE_NO> --raise <B|C> --reason "<the reviewer's finding>"` (recorded with its reason; tiers never go down). Size and breadth alone give Tier B (one six-lens reviewer, no fan-out, no G12).
   - **Resume a reviewer** that ran out of turns or context by its agent id (the Agent tool's resume) instead of spawning a fresh one, so its partial findings are kept.
   - If the reviewer can't run, the task **blocks**. Fail closed and never skip review silently. Only a task whose entry condition genuinely doesn't apply (for example, pure research notes) may use `--skip-review "<why>"` in step 10, and the reason is recorded.
9. **Tier C → human gate G12.** Halt with `$S/checkpoint.sh $ARGUMENTS halt "awaiting human gate G12 line <LINE_NO>"` and ask the user using the **Ask Contract**:
   - **What I'm asking:** approval to accept this change, in one sentence.
   - **What it does:** the behavior change in plain words, not the diff.
   - **Why:** how it serves the plan's goal.
   - **Risks:** what could go wrong, how likely it is, and how to undo it.
   End with "Reply `approve G12 <LINE_NO>` to continue." When the user replies with that, record their literal reply with `$S/checkpoint.sh $ARGUMENTS approve <LINE_NO> <sha> "<reply>"`. Never record an approval the user didn't give.
10. **Acceptance and check-off.** Run the task's `Acceptance:` check inside the worktree. It can be a runnable command, a file-exists test, or a regex match; for `[gate:human]`, wait for the user's literal approval phrase. On pass, run `$S/checkpoint.sh $ARGUMENTS complete <LINE_NO> "<verdict>"`. With the harness on, this **refuses** unless the gate, the review, and (for Tier C) the G12 approval all bind to the current head SHA. Write a one-paragraph summary to memory namespace `apex-execute` and advance.
11. **On failure:** run `$S/checkpoint.sh $ARGUMENTS fail <LINE_NO> "<reason, verbatim>" [--progress "<what this attempt closed>"]` (pass `--progress` only when the attempt committed fixes that closed earlier findings) and `$S/lessons.sh $ARGUMENTS fail "<stable failure signature>"`.
    - `ESCALATE:` means two failures in a row. Buy a second opinion from a *different* agent (fresh context, a different model if one is available) before retrying.
    - `RATCHET: FILE_LESSON` means this failure has happened before. File it with `$S/lessons.sh $ARGUMENTS add ...`, and where you can, add the guide or sensor that prevents it.
    - `HALTED` means a budget is spent: `APEX_ERROR_BUDGET` stalled failures (a failure without `--progress`, or whose head did not move since the previous failure), or `APEX_ATTEMPT_CAP` consecutive failures of any kind. The line names which counter fired. Surface it verbatim to the user and stop.
    - Review-loop cost is measured with `$S/status.sh $ARGUMENTS --review-metrics` (rounds, blocking rounds, minutes per round per task).
12. If the plan is complete (no unchecked tasks), the final gate has passed. Write `COMPLETE`, then **land the worktree** by running `$S/land.sh $ARGUMENTS`. With the harness on, land.sh re-runs the green gate on the final head and refuses to land any uncommitted, unreviewed code. Then exit, and do **not** call `ScheduleWakeup`.
13. Otherwise, call `ScheduleWakeup` with a delay matched to the next task's expected wait: 1200–1800s for non-urgent work, 270s when actively polling external state.

Respect the gates:
- `[gate:auto]` — run the Acceptance check, advance on pass.
- `[gate:human]` — set `halted: true` with `halt_reason: "awaiting human gate <id>"`, present the gate in Ask Contract form (what / what it does / why / risks), print "Reply 'approve <gate-id>' to continue," exit the loop.
- `[gate:partner:<email>]` — write a durable inbox item, halt with `halt_reason: "awaiting partner gate <id>"`.

Bounded reasoning: one task per iteration, one verdict gate, 30-minute timeout. Report truthfully: quote failures verbatim, name skipped steps, and never mark done what a sensor didn't verify. Don't make this a "make progress" loop — make it a "check this box" loop.

If `$ARGUMENTS` is empty, scan `.claude/plans/*-plan.md` for the most recently-modified plan and confirm with the user before iterating.
